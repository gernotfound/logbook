# Kinde — configurazione del provider per TheLogBook

## CF-03 · correzione audience ID token (17/11/2026, candidato v2.502.0)

**Evidenza osservata:** sul callback reale il browser segnala HTTP 503 con fase fissa `id-token-audience`. Questo prova il fallimento del controllo JOSE su `aud`, non fornisce il valore effettivo del claim né autorizza a leggere o registrare token. Il provider Cloudflare ha confermato in sola lettura la presenza dei cinque secret OAuth, senza valori, e un deploy del Worker Kinde privato.

**Root cause nel contratto applicativo:** il codice precedente validava l'ID token contro una audience indipendente (`KINDE_ID_TOKEN_AUDIENCE`); nelle fixture questa era l'URL issuer. OpenID Connect Core richiede invece che `aud` contenga il `client_id` dell'applicazione destinataria. La guida Kinde per il test delle proprie API mostra il client ID fra le audience dell'ID token. Lo stesso `client_id` viene già usato per PKCE/token exchange e `azp`: riutilizzarlo per `jwtVerify` elimina la configurazione divergente, **senza** accettare token destinati ad altre applicazioni. La verifica access token mantiene la distinta audience API.

**Cambio mirato:** la callback richiede che `aud` includa `KINDE_CLIENT_ID`, accettando come eventuale secondo destinatario soltanto l'issuer già verificato (forma array documentata da Kinde), tramite il verificatore, preservando RS256/JWKS, issuer, nonce, subject, `azp`, scadenze, email verificata, `at_hash`, state monouso, rate limit, D1 e revoca. Test firmati coprono ID token con `aud` client ID, audience non autorizzata e token con solo issuer. Nessuna lettura o modifica dei secret Cloudflare, di Kinde, del database o dei dati utente. **Il precedente secret `KINDE_ID_TOKEN_AUDIENCE` resta ancora presente nella configurazione Cloudflare e nel controllo provider, ma non è più letto dal runtime:** rimuoverlo solo con successivo cambiamento coordinato di script, test e risorse autorizzate, senza inventare valori.

**Prova ancora necessaria:** dopo gate CI exact-SHA, merge e readback del deployment sul vero `main`, un nuovo tentativo di login deve verificare il percorso reale; il successo del codice non è già un login riuscito. Non riutilizzare mai il vecchio URL callback o il code/state. Se il provider reale non emette il client ID in `aud`, l'errore resterà chiuso e occorrerà evidenza affidabile sul contratto Kinde, senza allargare l'allowlist. Le fasi diagnostiche temporanee restano da rimuovere prima del GO finale.

Fonti: https://www.itu.int/rec/dologin_pub.asp?id=T-REC-X.1285-202505-I%21%21PDF-E&lang=e&s=type e https://docs.kinde.com/developer-tools/your-apis/test-your-api-user-token/.


## CF-03 · callback Kinde: differenziare durata JWT e sessione (17/11/2026, candidato v2.501.0)

**Prova browser recente:** la callback hosted sulla v2.500.0 ha risposto `503 {"error":"authentication-unavailable","phase":"access-token-lifetime"}`. Questa fase viene prodotta *solo* quando il JWT access ha superato `jwtVerify` (firma RS256/JWKS, `iss`, audience, expiry), `azp`/subject/grant/iat/exp e poi `exp - iat > 86400`: **non è un token scaduto**, ma una durata del token superiore al tetto arbitrario della nostra callback. Il valore esatto e le impostazioni dell'app Kinde non sono stati letti, né servono dati o JWT reali. Non conservare mai URL completi di callback, code, state o token.

**Contratto ufficiale:** Kinde documenta [access token di default 86.400 s, configurabili per applicazione](https://docs.kinde.com/build/tokens/configure-tokens/) e **sconsiglia** di estenderne la durata oltre un giorno perché credenziali API sottratte potrebbero restare valide sino a `exp`. Nel nostro login OAuth, però, il JWT access arriva tramite **una sola** richiesta server-side `authorization_code` + PKCE dopo il consumo atomico dello stato D1 vincolato al cookie: non viene mai salvato, condiviso col browser né usato come credenziale API. La prova dell'identità richiede separatamente **ID token firmato RS256**, issuer/audience/client/subject corretti, nonce originario, emailVerified e ID-token `iat`/`exp` con durata massima 3600 s, oltre al binding `at_hash` se presente. La sessione TheLogBook è emessa dopo verifica owner D1 e mantiene scadenza/revoca indipendente.

**Correzione minima:** eliminare il limite `exp-iat <=86400` **soltanto** nel verificatore access JWT della callback monouso, preservando i controlli `exp > now`, `exp > iat`, `iat <= now+skew`, firma, issuer, audience, azp, sub e grant umano. Il verificatore **generale/API** rimane limitato a **900 s**, indipendentemente dalla configurazione Kinde. Il codice non considera un access token lungo autorizzazione persistente. Rimuovere `access-token-lifetime` dalla whitelist diagnostica della callback perché non più raggiungibile; mantenerlo per rifiuto verificabile sulle credenziali API. Fixture firmate verificano 24h, 24h+1 e 72h nella sola callback, rifiuti dell'API, token scaduti/falsi, email non verificata, nonce errato, ID token troppo lungo, D1 login, replay e no-success su guasto.

**Rischio residuo distinto dal login:** la durata reale degli access token Kinde è >24h per almeno il token osservato; potrebbe essere una personalizzazione del tenant o un offset d'emissione. **Prima del GO finale, verificare in Kinde il valore Tokens → access token expiry e ripristinare una durata appropriata**, senza modificare ora impostazioni OAuth/credenziali del provider né attribuire al test un valore esatto non visto. Token API sottratti restano a rischio fino a `exp`; il limite 900 s del nostro verificatore impedisce comunque l'accettazione da parte di quel boundary. La separazione dei ruoli rende il login indipendente da una TTL non rilevante per la sua sessione. Il collaudo con Kinde reale resta obbligatorio dopo main/gate/deploy; se emerge un'altra `phase`, non allentare automaticamente il controllo successivo. Eliminare le fasi diagnostiche temporanee prima del GO.


## CF-03 · login Kinde access-token: diagnosi verificabile (17/11/2026, candidato v2.500.0)

**Evidenza nuova del collaudo manuale:** dopo il deployment della v2.499.0, una callback hosted Kinde da un nuovo tentativo ha risposto `503 {"error":"authentication-unavailable","phase":"access-token"}`. Lo stato OAuth browser-bound è stato consumato, la risposta del token endpoint è stata accettata ed è iniziata la prova crittografica dell'access token, **prima** della verifica ID token e di qualunque sessione D1. Il precedente `phase=id-token` proveniva da un altro tentativo: non dimostra che il provider emetta sempre lo stesso tipo di JWT, né che i due errori abbiano la stessa causa.

**Codice verificato:** `cloudflare/auth/kinde-oauth-flow.mjs` passa già `audience: config.apiAudience` alla richiesta `/oauth2/auth`, insieme a `openid email profile`, PKCE S256, nonce e state. Non manca il parametro audience. `kinde-token-verifier.mjs` però trasformava in `invalid-kinde-token` tutti i fallimenti `jose.jwtVerify` e i claim custom, perciò `access-token` copriva un problema di chiave pubblica, un'audience o issuer diverso, una scadenza, il client `azp`, un subject o una vita token non consentiti. **La causa concreta non è ancora nota e i Secret non sono stati letti o cambiati.**

**Patch temporanea:** conserva RS256, JWKS, issuer, audience, azp, subject, iat/exp e il tetto di 24h esclusivo per il code-exchange monouso, e continua a non usare quel JWT come credenziale API. Dopo validazione e consumo del browser-bound state, i soli 503 possono esporre una fra le categorie fisse `access-token-format`, `access-token-audience`, `access-token-issuer`, `access-token-expired`, `access-token-key`, `access-token-signature`, `access-token-algorithm`, `access-token-client`, `access-token-subject`, `access-token-grant`, `access-token-timestamps`, `access-token-lifetime` oppure `access-token` generico. La classificazione JOSE usa soltanto `error.code` e, dove disponibile, il nome immutabile del claim `aud` o `iss`. Non serializza errori/causes/valori/JWT/header/email/UID/cookie/code/nonce/URL e non crea log o tracking.

**Hardening collegato e fondato sulle fonti:** Kinde documenta `gty` come array nei token M2M, per esempio `["client_credentials"]` (https://docs.kinde.com/machine-to-machine-applications/about-m2m/token-structure-and-claims-for-m2m-applications/). Il vecchio confronto solo stringa non intercettava questa forma. I token macchina sono ora rifiutati sia quando `gty` è stringa sia quando un array contiene `client_credentials`; il normale `gty: ["authorization_code"]` resta valido. La libreria `jose` già supporta `aud` come array con destinatari multipli: non introdurre un workaround o un'allowlist larga in assenza di evidenza. Kinde documenta i requisiti JWT in https://docs.kinde.com/developer-tools/about/using-kinde-without-an-sdk/ e https://docs.kinde.com/build/tokens/about-access-tokens/.

**Prossimo gate:** dopo CI exact-SHA, Main Release Gate, CodeQL, deploy Kinde privato e readback Cloudflare, fare **un nuovo tentativo** con l'account Kinde esistente da `https://thelogbook.me/verifica-accesso`. Comunicare **esclusivamente il valore `phase`** se resta 503 (senza URL callback, token, codice o password); una risposta 303 al frontend seguita da session-status 200 verificato dimostra solo l'accesso, non il GO di consenso/dati sanitari. Utilizzare la fase reale per correggere la root cause; non spegnere validazioni JWT, nessuna attivazione D1 sanitaria. La diagnostica temporanea deve essere rimossa prima del GO finale.


## CF-03 · ID token: individuazione del controllo fallito (17/11/2026, candidato v2.499.0)

**Evidenza runtime dell'owner:** dopo la diagnostica della v2.498.0, una nuova callback hosted Kinde è stata rifiutata con `503 {"error":"authentication-unavailable","phase":"id-token"}`. Questo dimostra che il processo ha completato il token exchange, ha accettato il formato della risposta, ha superato la verifica preliminare dell'access token ed è entrato nella verifica `jwtVerify` sull'ID token. **Non prova** ancora quale fra firma/JWKS, issuer, audience, scadenza o algoritmo sia fallito. `auth_principals` e `auth_sessions` non sono stati creati in quel percorso; non riutilizzare i codici OAuth già esposti nella console, non copiarli nel repository o nelle issue.

**Fonte Kinde e rischio:** la documentazione ufficiale `https://docs.kinde.com/build/tokens/about-id-tokens/` e le schede SDK descrivono il claim `aud` con esempi differenti (dominio dell'ambiente e identificatore dell'applicazione). L'ID token va quindi verificato rispetto all'audience effettivamente autorizzata, non semplicemente dichiarato valido perché la firma lo è. Il Worker usa `KINDE_ID_TOKEN_AUDIENCE` indipendente dalla audience API. Non è stato letto alcun valore segreto né il token reale, quindi **mismatch audience resta ipotesi**, al pari delle altre cause.

**Estensione minima diagnostica senza bypass:** la `KindeLoginProofError` temporanea separa il risultato della verifica JOSE in un insieme chiuso di sole etichette `id-token-audience`, `id-token-issuer`, `id-token-expired`, `id-token-key`, `id-token-signature`, `id-token-algorithm`; un errore non riconosciuto resta `id-token`. La classificazione utilizza esclusivamente `error.code` e, per `ERR_JWT_CLAIM_VALIDATION_FAILED`, la **sola chiave statica del claim** (aud/iss), mai `message`, valori dei claim, header, JWK, firma, token, nonce, UID, email o URL. La risposta continua a essere 503, senza cookie e con `no-store`, solo dopo la verifica e il consumo monouso dello state browser-bound. Non viene accettato nessun ID token precedentemente respinto: stessi parametri `jwtVerify` (issuer, audience configurata, RS256, clockTolerance), stesso `azp`, nonce, emailVerified, PKCE, guard D1, rate limit e revoca.

**Rimozione obbligatoria:** al termine del collaudo, eliminare tutte le fasi temporanee prima del GO login/fitness. Dopo il merge e readback Cloudflare, eseguire **un solo nuovo login** con l'account Kinde esistente e comunicare **soltanto `phase`**. Se compare `id-token-audience` verificare, senza mostrare credenziali o token, quale destinatario garantisce Kinde per quella app e l'attuale parametro dedicato; correggere l'esatto valore autorizzato, non allargare indiscriminatamente il validatore.

Il collaudo reale sul nuovo `main` v2.497.0 conferma ancora `503 authentication-unavailable` al ritorno `GET /api/auth/kinde/callback`. La callback maschera correttamente tutte le eccezioni sotto lo stesso status, ma questo impedisce di distinguere exchange Kinde, firma/claim JWT, owner D1 e creazione sessione, favorendo correzioni ipotetiche. Il provider Kinde è ancora collegato al Worker privato della v2.489.0; gli incrementi v2.490–v2.497 non dimostrano un nuovo login riuscito.

Questo dimostra assenza di sessioni/owner applicativi nel database letto, non il motivo del 503 o i contenuti del token. Nessun UID/email/hash/token consultato; nessuna mutazione SQL.

**Diagnostica circoscritta e temporanea:** soltanto su `503` della callback che ha già **consumato lo stato OAuth e verificato il cookie browser**, il backend aggiunge al JSON il campo `phase` con uno dei codici statici `token-transport`, `token-response`, `identity-input`, `access-token`, `id-token`, `id-claims`, `token-binding`, `principal-storage`, `session`. Non trasmette status/body di Kinde, claims, ragioni dettagliate, indirizzi email, nomi, UID, cookie, auth code, state, nonce, segreti o JWT; nessun logging, tracking, stato diagnostico o terza parte sono introdotti. Si distinguono proof JWT e storage con fasi non identificanti anche internamente. Le risposte restano `no-store` e la diagnostica non può autorizzare dati fitness.

**Prossima prova reale:** dopo Canonical/CodeQL exact-SHA, merge, gate main e readback Worker Kinde privato, effettuare un solo nuovo login dal documento `https://thelogbook.me/verifica-accesso`; riportare **soltanto `phase`** (senza l'URL della callback). Un 503 senza `phase` indica un problema prima/durante il consumo dello stato o del confine HTTP. Se il risultato è `token-response`, verificare Kinde token endpoint e client app senza stampare segreti; se è `access-token`/`id-token`/`id-claims`, confrontare provider reale con contratti di firma e claim; se `principal-storage`/`session`, verificare schema e write D1 con dati sintetici. **Rimuovere il campo diagnostico al termine della campagna con una PR verificata**, prima del GO Auth completo. Mai riutilizzare o divulgare auth code da tentativi falliti. Non allentare le firme, issuer/audience, email_verified, stato, nonce, PKCE o revoca per far scomparire il 503.


## CF-03 — HTTP 503 dopo callback valida: durata access token del provider (candidato v2.489.0)

**Evidenza reale:** dopo la correzione `scope` v2.488.0, l'owner conferma che Kinde mostra un utente creato e che un nuovo login termina con `503 authentication-unavailable` da `GET /api/auth/kinde/callback`, anziché il precedente 400. La singola callback non è accompagnata da una traccia di diagnostica dei passi interni, perciò **non attribuire il 503 a un singolo punto senza ulteriore prova**. Il flusso backend può fallire per scambio del codice, JWKS/claim, D1 o emissione della sessione; un 503 non autorizza bypass.

**Incompatibilità verificata codice/documentazione Kinde:** `createKindeAccessTokenVerifier` rifiuta access token con durata `exp - iat` oltre 900 secondi; Kinde [documenta come durata predefinita dell'access token 86.400 secondi (24 ore)](https://docs.kinde.com/build/tokens/configure-tokens/), configurabile per applicazione. La configurazione attuale del tenant non è stata riletta, quindi **non è ancora dimostrato che il token emesso in questo caso duri effettivamente 24 ore**. I test precedenti usavano token sintetici da 5 minuti e non coprivano il valore di default reale.

**Correzione a perimetro minimo:** nel **solo percorso trusted di callback** dopo exchange di code+PKCE e state monouso, il verificatore JWT accetta la durata documentata fino a 24 ore, e soltanto per completare immediatamente la prova di identità con `iss`/`aud`/`azp`, firma RS256/JWKS, `sub`, ID token firmato con nonce originale, emailVerified, binding `at_hash` e scadenza ID token <= 3600 secondi. Non salva o restituisce access token Kinde, non autorizza direttamente alcuna API sanitaria e non modifica la sessione D1 o i suoi fence. **Il verificatore generale per access token API resta fissato a 15 minuti**, quindi non si allarga l'autorizzazione dei servizi. I test su D1 e JWT sintetici coprono il default 24h, replay, falsificazioni, durata >24h e l'isolamento della policy 15 minuti.

**Prossimo GO:** CI exact-SHA, CodeQL, Main Gate, deploy/readback Worker Kinde privato e smoke frontend; poi un **nuovo** tentativo di login dall'origin diagnostico con lo stesso account Kinde già creato. Se persiste il 503, occorre isolare lo stadio effettivo senza esporre authorization code, state, cookie, password o token nei log o negli output. Il tentativo precedente è già consumato e non è riutilizzabile.

**Preferenza UX confermata dall'owner:** l'opzione Kinde *Ask for user first name and last name* è stata disattivata. Il pannello Kinde mostra un utente corrente; questa è evidenza di identità nel provider, **non** di sessione D1 o completamento della PWA.


**Catena di rilascio verificabile:** in precedenza il workflow `.github/workflows/cloudflare-kinde-private.yml` aveva un trigger push limitato a modifiche del solo file del workflow e `workflow_dispatch`: una modifica al codice `kinde-oauth-flow.mjs` poteva quindi essere integrata su `main` senza aggiornare il Worker privato, lasciando invariato il 400 nonostante i gate frontend. Il candidato amplia in modo mirato il trigger main-only a `cloudflare/auth/**` e `cloudflare/api/logout-worker.mjs`, mantenendo il controllo dello SHA di `main`, l'attestazione `Milestone Verification` trusted completa, la compilazione/dry-run, la pubblicazione esclusivamente del Worker privato e il readback no-public-URLs. Include un test di contratto CI per evitare regressioni del trigger. Prima e dopo ogni deploy il workflow verifica in lettura i binding autorizzati e **tutti e cinque i Secret OAuth** come `secret_text` (`--require-configured-oauth`), senza leggerne i valori; un preflight incompleto blocca la scrittura e un readback incompleto fa fallire la pipeline. Nessun deploy viene eseguito da un branch o prima dei gate.


## CF-03 — errore callback 400 dopo prima registrazione: correzione candidata (16/11/2026)

**Prova runtime riportata dall'owner:** il form OAuth ora raggiunge Kinde; il provider ha inviato la verifica email, ha rifiutato una password troppo breve e accettato una password conforme di almeno 15 caratteri. Il ritorno browser `GET /api/auth/kinde/callback` ha restituito `400 {"error":"authentication-unavailable"}`. L'URL osservato conteneva `code`, `state` e `scope=openid%20email%20profile`. **Non copiare codici OAuth, state o URL completi in issue o log:** sono dati transitori sensibili.

**Root cause dimostrata nel codice:** `callbackParameters` in `cloudflare/auth/kinde-oauth-flow.mjs` rifiutava qualsiasi chiave diversa da `state`, `code`, `error`, `error_description`; Kinde può includere anche `scope` nel redirect (documentazione ufficiale: https://docs.kinde.com/authenticate/custom-configurations/redirect-users/). La risposta HTTP 400 avveniva prima di leggere la riga D1 di OAuth state, scambiare il code o verificare i token. **Non si è ancora verificato** se dopo questa correzione emergeranno altri blocchi, ad esempio cookie Lax non trasmesso, state oltre la scadenza 10 minuti o token reali non accettati.

**Correzione:** accettare `scope` come parametro opzionale **soltanto se contiene l'insieme esatto dei tre scope richiesti** (`openid`, `email`, `profile`), in qualsiasi ordine ma senza duplicati, scope mancanti, aggiunti o spaziature malformate. Mantenere il rifiuto di parametri sconosciuti/duplicati, cookie browser `__Host-`, legame stato/nonce/PKCE, consumo atomico e verifica firma/audience; le callback senza `scope` restano valide. Test real-shaped su schema D1 corrente per successo, replay e rifiuti prima del consumo, più attraversamento gateway HTTP pubblico e Worker privato.

**Stato dell'attivazione:** nuovo tentativo con avvio OAuth fresco **solo dopo CI exact-SHA, merge, deploy Cloudflare e smoke**. La callback precedente non va ripetuta/reincollata. Gli avvisi `background.js` / `runtime.lastError` sembrano di un'estensione Chrome, e il suggerimento DOM password compare sulla pagina ospitata Kinde: non costituiscono evidenza della causa del 400. Dopo la correzione testare sessione, verifica email, reset e Google separatamente senza usare dati salute.

**Preferenza UX del PO:** registrazione solo email, senza richiedere nome e cognome. Kinde documenta l'opzione `Authentication experience → Ask for user first name and last name` disattivabile per applicazione (https://docs.kinde.com/authenticate/custom-configurations/authentication-experience/). Non modifica il contratto OAuth; da verificare e configurare nel pannello provider, separatamente da questo fix.


## CF-03 — HTTP 403 sulla pagina diagnostica: correzione candidata (16/11/2026)

**Segnalazione browser reale:** dalla pagina `/verifica-accesso`, il form nativo `POST /api/auth/kinde/start` termina con HTTP 403 prima del redirect a Kinde. L'HTML della v2.486.0 impostava `<meta name="referrer" content="no-referrer">`; la specifica Fetch/MDN documenta che in una navigazione POST non-CORS tale policy può produrre `Origin: null`, correttamente respinta dai controlli CSRF first-party dei due Worker. È una causa coerente con il rifiuto osservato, **non una traccia Network della singola richiesta**: altri fattori (es. policy Cloudflare) restano da escludere col collaudo dopo la correzione.

**Soluzione minima:** impostare soltanto sul documento diagnostico `Referrer-Policy: same-origin` tramite meta, senza allentare il requisito `Origin=https://thelogbook.me` o i controlli `Sec-Fetch-Site` dei Worker. Nessuna referenza a URL di callback/credential/token cambia; la policy non trasmette referrer ai domini esterni, incluso Kinde. Regressioni: unit test del meta e Playwright Chromium/WebKit che sottomette il vero form nello stesso origin e osserva l'header `Origin` senza contattare l'API reale. La conferma in Production richiede CI exact-SHA, deployment/smoke e un nuovo tentativo browser dell'owner; non considerare la prova sintetica equivalente al login hosted riuscito.


## CF-03 — accesso diagnostico first-party per collaudo provider (candidato v2.486.0)

**Stato:** il codice candidato e i test sintetici non dimostrano il login reale nel tenant.
